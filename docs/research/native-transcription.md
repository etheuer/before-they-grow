# Native transcription within the local-first boundary

**Decision — 2026-08-11:** add a small **local Expo native module** behind the mobile `Transcriber` contract. It uses only the OS speech APIs, makes an **on-device-only** attempt when the device, selected locale, installed model, and authorization permit it, and otherwise returns `unavailable` and opens manual transcript recovery. Keep recording durable audio independently with `expo-audio`; do not add a Before They Grow transcription service and do not silently fall back to a network recognizer.

This is intentionally a best-effort enhancement, not a prerequisite for saving a voice memory. It preserves the PRD's review-and-save boundary: automatic text is a draft, the parent edits it, audio may be saved with blank text, and a non-empty manual transcript may be saved if recording was unavailable.

## Why this approach

Expo has no official speech-to-text SDK: `expo-speech` is text-to-speech. `expo-audio` does provide recording permissions and durable document-directory recording, but not recognition. A native module is therefore required for the platform APIs. Expo says Expo Go can use only its bundled native libraries; a development build can include custom native code/configuration, and Expo Modules supports Swift and Kotlin modules. **Expo Go is not a test or release path for this feature; custom development builds and all release builds are required.** [Expo Speech](https://docs.expo.dev/versions/latest/sdk/speech/) · [Expo Audio](https://docs.expo.dev/versions/latest/sdk/audio/) · [Expo: custom native code](https://docs.expo.dev/workflow/customizing/)

Use one JS-facing capability check, not a promise that every phone can transcribe:

1. Record first and move/validate the audio as the normal capture path requires.
2. Ask the native module whether on-device transcription is usable for the explicit product locale (launch: `en-US`).
3. If usable, transcribe the local audio into a **draft**; otherwise return a reason such as `unsupported-device`, `unsupported-locale`, `model-missing`, `permission-denied`, `no-match`, or `service-error`.
4. Always show **Review transcript**. Never overwrite edited text with a late result. Save audio plus reviewed/empty text, or manual non-empty text without audio, exactly as specified in the PRD.

The module must expose a `cancel/dispose` operation. On Android, `SpeechRecognizer` methods run on the main thread and the caller must call `destroy()` when finished. [Android `SpeechRecognizer`](https://developer.android.com/reference/android/speech/SpeechRecognizer)

## Platform behavior and capability gates

| Platform | Native path to attempt | Offline/locale rule | Outcome when the gate fails |
| --- | --- | --- | --- |
| **iOS 26+** | Prefer `SpeechAnalyzer` + `SpeechTranscriber` on the recorded local audio. Apple documents that its transcriber modules do **not** send voice audio to Apple servers. | `SpeechTranscriber` exposes available/installed and downloadable locales; its assets are system-managed models. Download only after the parent chooses to do so. | No transcription; retain audio and open the editable field. |
| **iOS 13–25** | Use `SFSpeechURLRecognitionRequest` for the recorded file, but only when the locale recognizer is available **and** `supportsOnDeviceRecognition` is true; set `requiresOnDeviceRecognition = true`. | The on-device request keeps audio on device, but Apple says it is less accurate. A supported locale alone does not guarantee availability; some legacy locales need a network. Do not use that network path. | No transcription; manual recovery. |
| **Android API 33+** | Only when `isOnDeviceRecognitionAvailable()` is true, create the on-device `SpeechRecognizer`, then check support for the exact recognition intent. Feed one app-owned PCM source with `RecognizerIntent.EXTRA_AUDIO_SOURCE` and its channel/encoding/sample-rate extras, rather than asking a second recognizer to own the microphone. | The recognizer/provider and the selected locale/model must support that intent. Android's external-audio-source and segmented-session extras are API 33 and are explicitly implementation-dependent. Offer model download only as an explicit user action. | No transcription; manual recovery. |
| **Android API 31–32 and below** | Do not run a second microphone-owning recognizer beside the durable recorder in v1. API 31 can report/create an on-device recognizer, but the documented app-supplied audio source arrives only in API 33. | No claim of offline locale support on these devices. | Manual recovery after normal recording. |

Apple's legacy recognizer supports a specific locale, requires an availability check, can process an existing audio file, and stops recognition tasks lasting longer than one minute. Limit an automatic attempt to one minute (or make longer recordings manual-only) until a separately tested product limit exists. [Apple `SFSpeechRecognizer`](https://developer.apple.com/documentation/speech/sfspeechrecognizer) · [file request](https://developer.apple.com/documentation/speech/sfspeechurlrecognitionrequest) · [on-device support](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition) · [on-device requirement](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition)

`SpeechAnalyzer`/`SpeechTranscriber` are iOS 26 APIs, not a replacement for the iOS 13–25 fallback. Apple distinguishes these transcriber modules from `SFSpeechRecognizer` by stating that they do not send user voice audio to Apple servers. Their assets are downloaded from Apple and retained/managed by the system; that is a model download, not evidence that voice audio is sent to Apple. [Apple `SpeechAnalyzer`](https://developer.apple.com/documentation/speech/speechanalyzer) · [SpeechTranscriber](https://developer.apple.com/documentation/speech/speechtranscriber) · [asset inventory](https://developer.apple.com/documentation/speech/assetinventory) · [Apple speech permission guidance](https://developer.apple.com/documentation/speech/asking-permission-to-use-speech-recognition)

The Android adapter reads the completed durable recording and supplies decoded PCM through that API-33 file descriptor; the saved original remains the normal `expo-audio` file. The Android reference does not promise that every installed recognizer accepts an external source, which is why a positive support check is a hard gate rather than a fallback to a second microphone session.

Android documents that generic `SpeechRecognizer` implementations are *likely* to stream audio to remote servers. Its on-device availability check is API 31; `EXTRA_PREFER_OFFLINE` is only a preference and the recognizer may ignore it. Therefore neither `createSpeechRecognizer()` nor `EXTRA_PREFER_OFFLINE` is an acceptable privacy guarantee. The API 33 external source is an optional `ParcelFileDescriptor`; if a provider does not support it, the framework may open the microphone itself, so the support check and physical-device tests are release gates. [Android `SpeechRecognizer`](https://developer.android.com/reference/android/speech/SpeechRecognizer) · [Android `RecognizerIntent`](https://developer.android.com/reference/android/speech/RecognizerIntent#EXTRA_AUDIO_SOURCE)

## Permissions, data flow, and disclosures

- **Microphone:** request only from the record action. Expo Audio configures `NSMicrophoneUsageDescription` on iOS and `RECORD_AUDIO` on Android; Android requires runtime permission and recommends retaining text functionality after denial. [Expo Audio](https://docs.expo.dev/versions/latest/sdk/audio/) · [Android runtime permissions](https://developer.android.com/training/permissions/requesting)
- **iOS legacy speech:** request Speech authorization only if the legacy `SFSpeechRecognizer` path is actually about to run. `NSSpeechRecognitionUsageDescription` is mandatory or the app crashes; authorization is asynchronous and may be denied/restricted. The iOS 26 SpeechAnalyzer path is governed by its own availability/assets, while recording still needs microphone permission. [Apple: asking permission for speech recognition](https://developer.apple.com/documentation/speech/asking-permission-to-use-speech-recognition)
- **No Before They Grow transmission:** on the selected paths, recorded audio, draft text, reviewed text, and memory metadata remain in the app's local storage. The only network operation allowed by this design is a parent-approved OS model download; it does not send the recorded voice to a Before They Grow service.
- **Store forms:** Apple's App Privacy guidance says data processed only on device is not collected; Google Play says on-device-only processing is outside Data Safety collection. Complete both forms from the final data-flow/SDK inventory anyway. Apple requires all developer/third-party-partner collection to be considered, and Google requires data sent by libraries/SDKs to be reflected. [Apple App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/) · [Google Play Data safety](https://support.google.com/googleplay/android-developer/answer/10787469)
- **Do not make a remote-mode disclosure claim from API docs.** Android's generic API warns of likely remote streaming, but the platform references do not identify the installed provider, its retention, or its terms. If the product later enables a remote platform recognizer, first obtain and review that provider's primary privacy terms, update the just-in-time notice/privacy policy and store forms, and test the actual device flow. Until then, return manual recovery.

## Alternatives considered

| Approach | Expo/build fit | Boundary fit | Decision |
| --- | --- | --- | --- |
| `expo-speech` or Expo Go only | Available in Expo Go, but Expo Speech is TTS, not STT. | Cannot transcribe. | Reject. |
| **Local Expo Module wrapping the OS APIs** | Swift/Kotlin through Expo Modules; requires development/release builds. | Allows the strict availability gates above, no transcription backend, no package-selected remote fallback, and a small auditable surface. | **Select.** |
| `expo-speech-recognition` | Its maintainer's source says it wraps `SFSpeechRecognizer`/`SpeechRecognizer`, ships an Expo config plugin, and requires a development build. It can be useful for a time-boxed device spike. | It is a third-party wrapper, not an Expo or OS guarantee; its published compatibility table is its own test evidence and it currently targets legacy Apple speech rather than iOS 26 `SpeechAnalyzer`. | Do not make it the production boundary without source audit, version pinning, and the same device/privacy gates. |
| Generic platform/network recognition | Technically callable where a provider exists. | Android explicitly warns it is likely remote; provider processing cannot be substantiated from the Android API reference. | Reject for v1. |

Package facts above are cited to the package maintainer's own primary source, not treated as platform documentation: [`expo-speech-recognition` README at `a7a6c68`](https://github.com/jamsch/expo-speech-recognition/blob/a7a6c681b904af464fd4467fe6baa8ef807c01dc/README.md).

## Required failure and release evidence

Treat these as `unavailable`, never as a failed save: API/service absent; selected locale absent; model unavailable/download declined; microphone or iOS Speech permission denied/restricted; `isAvailable` false; no speech/no match; audio/service/busy/client error; cancellation; timeout; or a late callback after navigation. Preserve the completed audio before any transcription attempt and let the parent retry an attempt without rerecording. Android additionally defines language-not-supported/unavailable, network, no-match, busy, audio, and permission errors; these must map to the same recovery state. [Android `SpeechRecognizer` errors](https://developer.android.com/reference/android/speech/SpeechRecognizer)

Before calling this production-ready, demonstrate on physical devices: iOS 13–25 on-device SFSpeech and iOS 26 SpeechAnalyzer paths; Android API 33+ with an installed `en-US` on-device model and an unavailable-model/device case; airplane-mode recognition after model installation; permission denial/revocation; no-match; cancellation/re-record; process interruption; edit-before-late-result; save audio with empty text; and manual-only save. Verify that app-owned audio is intact and no automatic path opens a network recognizer. The official sources do **not** provide a complete OEM/model/locale compatibility or accuracy matrix, nor provider-retention terms; those claims require this device matrix and provider-specific primary evidence, not an assumption.
